# Conclusion

## Issue

In WebKit-based browsers, a request may be interrupted if another fuzzing
operation runs before the initial request completes. The browser aborts the
in-flight fetch and the resulting error surfaces as a console / page error
(`TypeError: Load failed`, `AbortError: Fetch is aborted`, `NSURLErrorDomain`
cancelled), which failed the Playwright tests on the `webkit` project.

## Root cause

- All API calls go through `src/services/api/getData.ts`. When a navigation,
  route switch or another UI/fuzzing operation supersedes an in-flight request,
  WebKit/Safari aborts the fetch and rejects the promise.
- Those rejections were **not** treated as "benign": they propagated as
  unhandled promise rejections, logged as console errors, and Playwright
  surfaced them as `pageerror`, failing the fuzz tests.

## Technical decisions

1. **Re-throw instead of swallowing or faking a non-200 response.** Returning
   `{ Status: 0 }` caused callers to log `console.error(/path returned 0)` and
   broke the Firefox fuzz test. Rethrowing lets callers keep their existing
   error paths while the interruption is made "invisible" at the global
   `unhandledrejection` layer via `event.preventDefault()`.
2. **Global suppression, not per-caller.** Because interruptions can happen on
   any in-flight request, handling them centrally in `errorLogger.ts` (plus
   test-side noise filters) is more robust than patching every caller. Only the
   two callers that explicitly logged `console.error` in a `catch` were hardened
   directly.
3. **Deterministic aborts.** Aborting fetches on `pagehide`/`beforeunload`
   through a real `AbortController` produces a recognizable `AbortError`
   instead of a browser-specific `TypeError: Load failed`, making detection
   reliable.

## Code-review reflection

Per the code-review skill output, the biggest concern was duplication of the
interruption-detection logic between `getData.ts` and `errorLogger.ts` (two
copies of `INTERRUPTED_ERROR_PATTERNS` and two nearly identical matchers).
This was resolved by extracting a single shared module
(`src/services/api/requestInterruption.ts`) and having both consumers import
from it, so the pattern list is maintained in one place. The same review also
surfaced `getUserCurentAvatarByID.ts` and `postComment.ts` as additional
`console.error` paths that could still surface interruption errors — both were
hardened against benign interruptions.
